[ACTIONED]
- Deterministic seeded gameplay RNG added in src/rng.ts.
- GameState now stores runSeed and rngState.
- Gameplay randomness in engine.ts no longer calls Math.random directly.
- createInitialState accepts an optional runSeedOverride, allowing a known
  seed to reproduce a run during debugging without changing normal starts.
- Level Up weighted choice generation now consumes the GameState RNG.
- All five currently implemented Spheres are valid Level-Up sources; the
  previous vertical-slice source gate no longer hides Shotgun/Aura.
- scripts/audit-gameplay.mjs upgraded to coverage-v2 with explicit
  Blueprint -> Code+Integrated coverage for the final Ability vocabulary,
  Ability evolution references, Sphere branch references, Modifiers,
  Geometry, Runes and Artifact target coverage.
- Semantic review flags were added so code presence is not treated as fully
  faithful gameplay semantics.
- RNG and Level-Up regression coverage was added.
- Boss telegraph timing moved into a shared pure runtime contract; brittle
  literal-timing checks in the boss test were reduced to integration checks.

[REVIEWED — NOT A BLOCKER]
- Echo Drones are currently appended to the runtime Network graph through
  buildRuntimeNetworkNodes(); the earlier claim that Drones could never be
  true Network nodes is stale for the current branch.
- Renderer-only Math.random usage may remain for visual jitter; this is not
  part of gameplay determinism.

[SEMANTIC GAP]
- shield_echo_guard still describes per-Sphere protective charges while the
  current runtime stores shieldCharges at PlayerState level. This remains a
  manual-review item and must be resolved before calling the branch fully
  Blueprint-faithful.

[NOT YET ACTIONED]
- Replace remaining source-regex gameplay tests with behavioral contracts.
- Add lint to CI and verify main-branch workflow coverage.
- Identify the authoritative workflow file before changing CI; do not create
  a duplicate workflow blindly.
- Controlled decomposition of engine.ts / renderer.ts / App.tsx remains
  postponed until the gameplay audit and behavioral baseline are stable.

--- PLAYTEST ACCEPTANCE CRITERIA / LEVEL-UP ---

Purpose:
Validate the new Level-Up choice flow in a real APK run before numerical tuning or further structural changes.

A playtest is considered SUCCESSFUL when, during a normal 10-15 minute run:

1. Choice quality
- Every Level-Up presents exactly 3 usable choices.
- No obviously dead or already-invalid choice is offered.
- No immediate duplicate of the same logical card appears across consecutive Level-Ups when enough alternatives exist.
- Choices remain understandable from the current build context.

2. Build coherence
- The player can recognize a developing build direction rather than receiving three unrelated upgrades repeatedly.
- Character/sphere/build affinity is noticeable but does not make the screen feel predetermined.
- It remains possible to pivot the build when a useful alternative appears.

3. RNG feel
- The same card does not appear so frequently that Level-Up feels scripted.
- The player does not experience long stretches where one source dominates without meaningful alternatives.
- Pity behavior is not visually obvious or exploitable.
- Different runs with different seeded/random outcomes can develop meaningfully different builds.

4. Progression pressure
- Early Level-Ups offer understandable foundational growth.
- Mid-run Level-Ups increasingly present meaningful choices between strengthening the current build and opening a new direction.
- The player should not feel forced into a weak option merely because of source composition.

5. UX / pacing
- Level-Up interaction is immediate and readable.
- No visible frame hitch, state reset, stuck selection, or duplicated UI.
- Selecting a card clearly resumes the run with the intended upgrade applied.

6. Failure conditions
Any of the following fails the playtest:
- fewer than 3 choices;
- dead/invalid choices visible;
- repeated identical logical card across consecutive screens despite sufficient alternatives;
- obvious forced Ability/Sphere/Modifier pattern;
- build becomes effectively predetermined by RNG protection;
- upgrade selection causes combat/progression state corruption;
- noticeable Level-Up UI/performance regression.

Playtest record should note:
- run duration;
- approximate Level-Up count;
- notable repeated choices;
- source distribution observed qualitatively;
- whether build direction felt coherent;
- any dead/invalid choice;
- any UX/performance issue;
- screenshots/video for any failure case.

Human playtest is required for acceptance. Passing automated CI does not by itself mark these criteria as passed.
