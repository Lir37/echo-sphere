0A. REVISION 1.2 — QUALITY / SYSTEMIC ALIGNMENT AMENDMENT
======================================================================

This amendment is part of the authoritative Blueprint and takes
precedence over older wording inside this document when a conflict exists.

PURPOSE:
The September 25 quality audit identified several places where the
implemented game systems were mechanically simpler than the intended
product identity. The target is NOT to reduce the final design scope.
The target is to make the existing core systems more readable,
meaningful and internally consistent.

1. CONTACT DAMAGE

Contact damage must not behave as frame-by-frame HP shredding.

RULE:
- after successful player damage, apply 0.60 sec post-hit grace;
- this grace is separate from Dash invulnerability;
- repeated contact during grace does not deal additional damage;
- visual feedback must communicate the hit and short protection window.

This rule applies to enemy contact and repeated close-range collision
sources routed through the same player-damage function. It does not
remove projectile danger or boss telegraphed attacks.

2. CRITICAL HITS

Final baseline:
CRIT_BASE = 5%
CRIT_MULTIPLIER_BASE = 1.50x
CRIT_HARD_CAP = 75%

All ordinary crit sources are additive before the hard cap.
Sphere-specific bonuses may add to the same pool.
A system that intentionally bypasses the cap must be an explicit
exception in its own specification.

3. RESONANCE MODEL

Resonance is a real run resource, not merely per-Sphere hit counters.

AUTHORITATIVE TARGET:
- 0..100 baseline charge;
- charge comes from Sphere hits, completed Geometry, network events,
  character effects, Artifacts and selected Runes;
- reaching 100 triggers a formation-specific Resonance Event;
- temporary overflow to 150 is allowed only through explicit effects.

Per-Sphere counters may remain as implementation details for local
formation triggers, but they must not replace the player-level Resonance
resource in the final architecture.

4. ARTIFACT SET COMPLETION

Completing an Artifact Set must change gameplay behavior.
A flat universal damage multiplier is NOT a valid Set-completion effect.

Current intended behavioral direction:

RESONANCE GRID:
completed Set accelerates formation-driven Resonance events.

ECHO ARCHITECTURE:
completed Set creates real relay events between linked Spheres.

SINGULARITY PATH:
completed Set creates a conditional high-risk execution/echo behavior
when the build is intentionally concentrated.

Set completion must remain visible in the UI and readable as a build
milestone.

5. ELITE ENEMIES

An Elite is not only a larger HP/damage unit.

At least one Elite family must interact with the game's core system.
The first implementation target is LINK BREAKER:
- periodically targets a nearby Sphere;
- temporarily removes that Sphere from active Network participation;
- clearly telegraphs the disruption;
- creates a meaningful reason to reposition or protect the Network.

Future Elite families may target Resonance, Geometry or resource flow.
Do not create many Elite mechanics before the first one is playtested.

6. LEVEL-UP RNG QUALITY

Level-Up choice generation remains the core build-construction engine.
The final model explicitly requires:
- build affinity;
- character affinity;
- unfinished-system pressure;
- duplicate suppression;
- dead-option suppression;
- pity weighting;
- rarity/reward-source rules;
- limited reroll;
- Lock;
- later-meta Ban.

The player must never be guaranteed a specific build item, but should
also not be trapped by repeated functionally dead choices.

7. SEEDED RUN RNG

Gameplay randomness must use the run RNG state.
Renderer-only cosmetic jitter may remain non-deterministic.
A run should be reproducible when the same seed and equivalent inputs are
used, which is important for balance debugging and future telemetry.

8. NETWORK READABILITY

Network topology is the game's defining mechanic.
Any feature that changes Network structure must have:
- immediate visual feedback;
- readable active/inactive state;
- clear indication when a Sphere loses Network participation;
- enough persistence that the player can understand what happened.

Ghost Snap is now an approved UX direction for Sphere repositioning:
while moving a Sphere, show a preview of the resulting links and likely
Geometry before the player commits the placement.

9. FORMATION MEMORY

When a Sphere is removed, disrupted or repositioned, the player should
be able to understand which formation was broken and which formation can
be rebuilt. This may be implemented as a short-lived ghost outline,
link fade or Geometry echo.

10. PERFORMANCE GUARDRAIL

analyzeSphereNetwork() is gameplay-critical and may be called by many
systems. The implementation must be profiled before optimization.
If profiling confirms redundant same-frame recomputation, use a
frame/run cache rather than rewriting the Network algorithm blindly.

11. SCOPE DECISION

This amendment does NOT cut the final target roster.

Preserve:
- 10 Sphere types;
- 7 Geometry states;
- 90-120 Artifact target;
- 15+ enemy roles;
- 8 boss families;
- full Character target;
- long-term meta systems.

Development is phased, but the Blueprint remains the full target.
Scope reductions may be made only from actual playtest evidence,
production constraints or a deliberate product decision, not from an
external reviewer's arbitrary launch-scope recommendation.

12. DEVELOPMENT ORDER AFTER THIS AMENDMENT

P0:
- contact damage cadence;
- crit normalization;
- Resonance architecture alignment;
- Network disruption readability.

P1:
- Ghost Snap placement preview;
- Formation Memory;
- Artifact Set behavioral polish;
- first Link Breaker Elite playtest.

P2:
- Level-Up RNG protections;
- Network performance profiling/cache if justified;
- deeper Elite/Network interactions;
- broader Artifact and Geometry content.

1. DESIGN REFERENCE: MAGIC SURVIVAL
======================================================================

Magic Survival is used only as a benchmark for systemic depth and
long-term buildcraft.

Research consulted during validation:
- unofficial Magic Survival wiki, current pages crawled in September 2026;
- Magic, Artifact, Class, Research and Basics pages;
- community build references and mechanics notes.

The benchmark shows the value of:
- separate combat and passive progression layers;
- repeated level-up decisions;
- persistent Class/Research progression;
- Artifact rewards independent from level-up;
- Synergy created by collections of Artifacts;
- merchants and rerolls;
- special field pickups;
- rare legendary reward moments;
- build-specific value changing over time;
- explicit formulas and community theorycrafting.

The benchmark also confirms that its RNG is a real build-construction
constraint: Level Up normally offers three random choices, existing
choices are weighted, some systems can create four choices, and Artifact
rewards can also be rerolled in specific contexts.

ECHO SPHERE does NOT copy:
- names;
- characters;
- art;
- lore;
- UI layouts;
- descriptions;
- exact abilities;
- exact Artifact designs;
- exact progression tables.

Instead, ECHO SPHERE keeps the structural lesson and makes NETWORK +
GEOMETRY + RESONANCE its own core system.

Benchmark facts and source references are listed in Appendix A.

Distinctive product chain:

 -> MODIFIERS

 -> GEOMETRY
 -> RESONANCE
 -> RUNE EVENTS
 -> ARTIFACTS

3. PLAYER EXPERIENCE
======================================================================

The player must:
- understand movement immediately;
- survive without manual aiming;
- make frequent but understandable choices;
- feel that Sphere placement matters;
- recognize build direction;
- adapt to RNG without waiting for one perfect item;
- read enemy danger;
- understand boss attacks before damage lands;
- feel major reward moments;
- understand death;
- want another run.

The intended sensation is:
EARLY:
"I am building."
MID:
"My network now behaves differently."
LATE:
"I engineered this build on purpose."

4. RUN LENGTH
======================================================================

NORMAL RUN:
15-20 minutes.

EXTENDED RUN:
20-30 minutes.

ENDLESS:
30+ minutes.

Design target:
the main run should reach its decisive build pivot before minute 12-14.

Boss cadence:
- first major boss approximately 5-6 min;
- second major boss approximately 10-12 min;
- final encounter approximately 15-20 min.

Exact timing is configurable by stage.

======================================================================
17. NETWORK
======================================================================

Every active Sphere is a Network Node.

A Link is active when:
distance <= LINK_DISTANCE
and both nodes are alive.

Current repository uses a pixel-space implementation around 220 px.
The final design treats this as a configurable gamefield distance,
not a fixed real-world measurement.

Base target:
LINK_DISTANCE = 220 logical field units.

Each Link has:
- endpoints;
- distance;
- strength;
- resonance state.

Network statistics:
- node count;
- link count;
- average link distance;
- density;
- stability;
- active geometry;
- Resonance charge.

======================================================================
48. DAMAGE MODEL
======================================================================

Base damage is separated into categories.

FinalDamage =
BaseDamage
× SphereMultiplier
× ModifierMultiplier
× NetworkMultiplier
× ArtifactMultiplier
× ResonanceMultiplier
× CritMultiplier
× CharacterMultiplier

Not every effect is multiplicative.

Stacking policy:
- same-family small bonuses generally add;
- category-level bonuses may multiply;
- character signatures use explicit category;
- critical multiplier is applied only on a successful crit;
- diminishing returns apply to extreme haste, radius and density.

No uncontrolled chain of multiplicative bonuses.

======================================================================
49. COOLDOWN MODEL
======================================================================

FinalCooldown =
BaseCooldown
× LocalModifier
× AbilityModifier
× CharacterModifier
× ArtifactModifier
× NetworkModifier

Hard floor:
20% of BaseCooldown.

Temporary exceptions may bypass the floor for a short effect.

Every override must be explicit in data.

======================================================================

0-100%.

- Breach;
- Sniper;

- Precision.

Never let several independent systems multiply crit chance and crit
multiplier without caps.

51. STATUS MODEL
======================================================================

intensity
stacks
source
interaction flags.

Rules:
- Burn = DoT;
- Poison = stacking DoT;
- Freeze = control;
- Breach = defense reduction;
- Mark = targeted amplification;
- Fracture = reaction state.

Alchemist can create:

Freeze + Poison = Cryotoxin
Fire + Freeze = Thermal Shock

Reactions consume participating statuses.

======================================================================
52. NETWORK BALANCE
======================================================================

Define:

DENSITY =
activeLinks / maxPossibleLinks

At high density:
diminishing returns.

Suggested:
D <= 0.60
full efficiency.

0.60 < D <= 0.80
90% incremental efficiency.

D > 0.80
70% incremental efficiency.

This keeps compact networks good without making "stack everything in
one point" the dominant answer.

APPENDIX C. CURRENT NETWORK / DUPLICATE-SPHERE / PERFORMANCE AMENDMENT
2026-09-27
======================================================================

This addendum supersedes the earlier overlapping-Geometry rule where it
conflicts with the following current gameplay contract.

C1. ACTIVE GEOMETRY OWNERSHIP

Physical Links remain canonical Network infrastructure.

Active Geometry is a higher-level formation state.

A Sphere may belong to only ONE active Geometry at a time.

Up to TWO active Geometry formations may exist simultaneously.

Multiple formations are allowed only when their Sphere-node sets are
disjoint.

The renderer may show physical Links between all linked nodes, but a
Sphere must never receive multiple simultaneous Geometry bonuses through
overlapping formations.

Formation resolution is deterministic and centralized in network.ts.

Priority favors exact/specific formations over broad compactness when they
compete for the same nodes.

C2. DUPLICATE SPHERE LIMIT

Default run rule:
MAX_SAME_SPHERE_COPIES = 2.

This applies per Sphere type.

Purpose:
- prevents degenerate stacking such as five Gravity Spheres;
- preserves meaningful choice between Sphere families;
- creates a natural reason to expand total Sphere capacity;
- keeps late-run builds broad rather than collapsing into one repeated
  control effect.

The limit is a centralized balance constant and may be changed by a future
explicit system, Artifact or challenge mode. It must not be silently
overridden by individual placement code.

C3. GRAVITY CONTROL

Gravity remains a control Sphere, not a permanent enemy lock.

The duplicate cap is the first anti-lock gate.

Future balance work must additionally test:
- 2 Gravity + Freeze;
- 2 Gravity + Cluster;
- 2 Gravity + slow;
- enhanced Gravity final branches;
- long-run control uptime.

Control builds must create windows of safety without deleting meaningful
enemy pressure.

C4. NETWORK HUD TOOLTIP

Holding an active Geometry badge for ~0.5 sec reveals a compact tactical
tooltip describing its current gameplay role.

Tooltip is informational only and does not alter state.

C5. PERFORMANCE

APK size is NOT treated as the primary explanation for mobile frame-rate
degradation.

The current runtime risk profile is:
- repeated Canvas path/gradient/shadow work;
- transient VFX allocation;
- per-frame Network analysis;
- repeated distance/target scans;
- increasing enemy density;
- render workload growth over time.

Current mitigations:
- Network frame cache reused across update and render;
- ability/gravity/render Network reads routed through the cache;
- transient VFX budgets are capped;
- renderer uses adaptive stride for high transient load;
- heavy runtime content remains 2.5D/Canvas and asset-light.

The next performance gate must measure:
- frame time;
- enemy count;
- particle count;
- projectile count;
- Network links;
- mobile stability through at least a 10-15 minute run.

Do not blame small APK size without runtime profiling evidence.

C6. ARCHIVE DISCOVERY

Sphere discovery now has an explicit PlayerState record:
knownSphereTypes.

Placement records the first encounter immediately, and Archive sync also
reads that state. This exists to make Sphere discovery durable even when
the active Sphere is removed before the run ends.

APPENDIX D. 2D/2.5D PRODUCTION ART PIPELINE
2026-09-27
======================================================================

D1. PRODUCTION DIRECTION

ECHO SPHERE's production visual direction is 2D/2.5D-first.

The game must NOT return to mass 3D/GLB production at the current stage.

Existing GLB/3D work is historical/parked unless a future product decision
explicitly reopens it.

The production path for Characters, Spheres, Enemies and Bosses is:

CONCEPT ART
-> PRODUCTION ASSET SHEET
-> SPRITE / LAYERED RASTER ASSETS
-> CANVAS 2.5D RENDERING
-> PROCEDURAL VFX / ANIMATION
-> IN-GAME ASSET

The purpose is to preserve the visual quality of the concept direction
without introducing a heavy 3D asset pipeline.

D2. NO PRIMITIVE SUBSTITUTION

Production Characters, Spheres, Enemies and Bosses must not be represented
by generic Canvas primitives when an approved production asset exists.

Canvas primitives remain valid for:
- VFX;
- particles;
- trails;
- rings;
- telegraphs;
- debug visualization;
- simple auxiliary geometry.

They are not a substitute for the approved character/enemy/Sphere artwork.

D3. CONCEPT ART IS NOT THE FINAL GAME ASSET

A generated concept collage is a visual master/reference.

It must be converted into production-ready assets before gameplay
integration.

Production asset requirements may include:
- transparent background;
- fixed orthographic camera;
- consistent object scale;
- consistent visual orientation;
- frame-safe margins;
- separate animation frames or sprite sheets;
- optional separated layers for Core, shell, rings, petals and energy;
- deterministic naming;
- manifest describing frame dimensions, FPS and animation loops.

D4. ANIMATION MODEL

The preferred animation model is sprite/layer animation rendered by Canvas.

Characters, Spheres and enemies should support, where appropriate:
- idle;
- movement;
- attack;
- hit;
- shield/defense;
- death;
- special/ability;
- boss phase.

Animation should be achieved through:
- sprite frame changes;
- layer transforms;
- rotation;
- scale;
- squash/stretch;
- parallax;
- procedural VFX.

Do not create a 3D model merely to obtain basic animation.

D5. LAYERED 2.5D

Important assets may be split into inexpensive layers.

Example:

ASSET
- base/silhouette
- core
- shell/facets
- rings
- energy
- glow

The renderer may animate these independently.

This is preferred when it creates more visual depth for materially lower
runtime and production complexity than a full 3D model.

D6. VFX SEPARATION

Art assets and procedural VFX are separate systems.

High-quality authored artwork provides:
- silhouette;
- shape language;
- material appearance;
- character identity.

Canvas VFX provides:
- glow;
- particles;
- trails;
- impact flashes;
- status effects;
- telegraphs;
- resonance pulses.

Performance-sensitive high-count VFX must continue to use the established
bounded/hybrid approach. Do not globally restore expensive blur operations
just because authored assets have been introduced.

D7. ASSET PRODUCTION WORKFLOW

For a new production asset:

1. Generate or approve the concept.
2. Produce a dedicated asset sheet, not merely a gameplay screenshot.
3. Extract/prepare individual frames or layers.
4. Validate transparency, scale, orientation and readability.
5. Add assets to the repository under the designated 2D/2.5D asset tree.
6. Add or update the asset manifest.
7. Connect the asset through the existing renderer/animation abstraction.
8. Verify the asset in the actual game.
9. Run CI and inspect the resulting APK/web visual artifact.
10. Only after successful PlayerCheck is the asset considered production-ready.

The model/tooling may prepare the artwork and repository files directly when
the required binary-file handoff is available. If a generation interface
cannot expose binary bytes directly, the fallback is a generated asset
followed by an explicit repository upload step. In both cases the target
state is the same: the approved asset must exist in the repository and be
referenced by the game, not remain only as a chat image.

D8. FIRST PRODUCTION TARGET

The first production asset should be SPHERIST.

Target initial package:
- front/side/3-4 visual reference;
- idle animation;
- movement animation;
- attack animation;
- shield animation;
- hit animation;
- death animation;
- Core/ring/glow layers where useful;
- asset manifest.

This package becomes the reference implementation for the rest of the
asset pipeline.

D9. VISUAL QUALITY RULE

The visual target is the expressive pre-optimization ECHO SPHERE look,
with only the minimum glow reduction required for mobile performance.

Optimization must remove waste, not visual identity.

If performance becomes a problem, profile and optimize:
- repeated draw work;
- excessive transient allocations;
- high-count VFX;
- unnecessary blur;
- redundant geometry;
- texture sizes;
- draw-call density.

Do NOT solve performance by replacing authored artwork with primitive
placeholders.

D10. 3D / GLB GATE

3D/GLB production remains PARKED.

Reopening mass 3D production requires an explicit product decision after:
- the 2D/2.5D game is visually and mechanically validated;
- retention/gameplay quality justify additional production cost;
- device performance is understood;
- the production pipeline can be maintained reliably.

GEOMETRY 2.0 — DOMINANCE MODEL
======================================================================

DATE: 2026-10-03
STATUS: IMPLEMENTED IN new-desing

The Network now separates three layers:

1. PHYSICAL LINKS
   Canonical infrastructure. Links exist whenever two live Network Nodes
   are within LINK_DISTANCE.

2. FORMATION CANDIDATES
   Every valid Geometry is evaluated independently. A Sphere may therefore
   participate in more than one valid formation.

3.1 TWO-SLOT PLAYER CONTROL
The Network has exactly two combat-active formation slots:
- DOMINANT: full formation effectiveness and owner of the next player-level Resonance Event.
- SECONDARY: active at 50% effectiveness for numeric formation bonuses and reduced/discrete proc value where a direct half is impossible.

A Sphere may participate in both active formations. Adding a new Sphere can therefore
complete a secondary formation without removing the established dominant formation.

The active pair is still limited to two formations. A third valid Geometry remains
inactive and grants no formation bonus.

HUD SWAP:
The player may swap the two active slots directly from the Network HUD by dragging one
formation onto the other. This is a slot-order change, not creation of a third formation.
After the swap, the dragged formation becomes DOMINANT and the other becomes SECONDARY.
The chosen order persists while both formations remain valid. If one disappears, the
Network normalizes the remaining active slots from the valid candidates.

SECONDARY READABILITY:
The HUD presents the dominant formation as the visually stronger item, then shows
"+" and the secondary formation with reduced visual emphasis. Its detail popup must
highlight the currently active portion of each bonus while dimming the full/reference
portion so the player can immediately see that the secondary layer is partial.

3. ACTIVE GEOMETRY LAYERS
   At most two formations are combat-active:
   - DOMINANT FORMATION: primary Network identity and owner of the next
     player-level Resonance Event.
   - SECONDARY FORMATION: retains its own local Geometry mechanics, but
     does not override the dominant Resonance event.

DOMINANCE SCORE:

score =
  strength * 100
  + specificity bonus
  + size bonus

Specificity:
LINE 0
TRIANGLE 1
CLUSTER 2
SQUARE 5
RING 3
LATTICE 5
FRACTAL 7

Size bonus:
+1.5 per node above 3, capped at +6.

This means geometric precision is the main factor. A weak higher-order
shape does not automatically beat a strong lower-order shape.

FORMATION INERTIA:

When a dominant formation already exists, another formation must exceed
its dominance score by 10 points to take over.

The old dominant formation is immediately lost if it is no longer valid.

This prevents visual jitter and accidental Network identity changes while
moving a Sphere a few pixels.

HOW THE PLAYER CHANGES DOMINANCE:

Dominance is normally changed through placement and formation quality.
For an already active pair, the player may also explicitly swap DOMINANT and SECONDARY
in the Network HUD by dragging one slot onto the other.

Placement remains responsible for discovering and validating formations:
- move an existing Sphere;
- move a fourth/fifth Sphere into a position that completes a stronger form;
- pull a Sphere away so the current form weakens or breaks;
- use Ghost Snap to preview the resulting dominant Geometry before commit.

Example:
A 3-Sphere Triangle can remain dominant after a fourth Sphere is added.
The fourth Sphere does not evict the Triangle merely because it is nearby.
If the four Spheres are arranged into a sufficiently strong Square, Square
can become dominant. To return to Triangle, the player weakens/breaks the
Square arrangement or rebuilds the Triangle.

OVERLAP RULE:

The previous "one Sphere belongs to only one Geometry" rule is replaced.
Overlapping Geometry is allowed, but only the two highest-quality
formations become active. This preserves build interaction without
allowing uncontrolled multi-formation stacking.

RESONANCE:

The dominant Geometry determines which formation-specific Resonance Event
fires at 100 Resonance charge. Static type priority is no longer used.

GHOST SNAP:

Ghost Snap reports the prospective dominant Geometry, so the placement
preview directly answers "what will my Network become if I put the Sphere
here?"

SQUARE ROLE CLEANUP:

Square no longer receives generic +8% damage, -6% attack delay or +1
projectile pierce. Its identity remains defensive/stability-oriented:
formation hits build shield charges, and Square Resonance provides a
defensive burst. This keeps Square from becoming a universal combat
multiplier.
