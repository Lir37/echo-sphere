ECHO SPHERE — RULES FOR SPHERE DESIGN AND VISUAL PRODUCTION v1.0
Дата: 2026-09-29

НАЗНАЧЕНИЕ
Этот документ является обязательным правилом создания визуала всех Sphere.
Sphere строится по approved reference sheet как по художественно-техническому макету.
Reference sheet не является готовым игровым спрайтом.

1. ОСНОВНОЙ ПРИНЦИП
Reference sheet = construction/layout source.
Нельзя просто вставлять целую картинку Sphere в Canvas.
Нельзя использовать full-sheet crop как финальный visual asset.
Нельзя заменять утверждённую конструкцию новой самостоятельной геометрией без подтверждённой причины.

2. РАЗБОР НА ДЕТАЛИ
Из reference sheet выделяются реальные конструктивные элементы:
- корпусные панели;
- кристаллы;
- энергетическое ядро;
- кольца и орбитальные элементы;
- стеклянные/прозрачные элементы;
- крепёжные и декоративные элементы, если они являются частью утверждённого дизайна.
Каждый значимый элемент должен существовать как отдельный transparent production asset, если его требуется анимировать или менять независимо.

3. МАТЕРИАЛЫ
Каждый asset сохраняет материал, подразумеваемый reference:
- металл: грани, отражения, световые блики и затемнение;
- кристалл: фаски, цветные грани, внутреннее свечение;
- стекло/энергетика: прозрачность, alpha, glow и видимые слои;
- emissive элементы: отдельная управляемая интенсивность.
Не допускается рисовать поверх детали простую цветную геометрическую замену вместо её материала.

4. ПРОЗРАЧНОСТЬ
Фон reference sheet должен быть удалён.
В asset сохраняется только сама деталь и необходимая для неё прозрачная область.
Контур не должен содержать прямоугольник, фон листа или тёмную подложку reference.

5. СБОРКА 2.5D
Canvas является сборщиком конструкции.
Каждая деталь получает:
- позицию/anchor;
- масштаб;
- rotation;
- depth/layer;
- opacity;
- animation state.
Сборка должна иметь осмысленные передний, средний и задний слои.
Детали не должны выглядеть как случайно наклеенные картинки.

6. АНИМАЦИЯ
Каждый значимый элемент должен иметь собственное допустимое поведение.
Минимальный набор:
- idle: лёгкое живое состояние;
- charge/attack: реакция на действие Sphere;
- hit: короткая реакция;
- mutation: изменение или замена соответствующих деталей;
- death/disabled, если состояние предусмотрено механикой.
Анимация должна быть небольшой и привязанной к функции детали.
Нельзя вращать всю Sphere целиком только ради ощущения движения.

7. ЭФФЕКТЫ
FX усиливают существующие материалы, но не заменяют их.
Glow, bloom, particles, recoil, light sweep и screen-space effects должны работать поверх authored assets.
Canvas FX не должны рисовать новую силуэтную Sphere поверх reference-конструкции.

8. ВИДЫ И ГЛУБИНА
Если reference sheet содержит front/side/back/3/4 views и exploded structure, они используются для определения:
- положения деталей;
- глубины;
- перекрытия;
- формы и масштаба компонентов.
Exploded view является схемой конструкции, а не обязательным кадром игрового интерфейса.

9. МУТАЦИИ
Mutation I и Mutation II строятся из той же базовой конструкции.
Если mutation меняет компонент, меняется соответствующий asset или его material/state.
Нельзя полностью заменять Sphere другой случайной картинкой, если reference sheet показывает эволюцию отдельных деталей.

10. КАЧЕСТВО
Финальный asset должен быть рассчитан на игровой размер с запасом по разрешению.
Нужны чистые alpha-контуры и читаемые материалы.
При уменьшении до размера Sphere детали должны сохранять силуэт, цветовую иерархию и ключевые highlights.

11. ПРОИЗВОДСТВЕННЫЙ PIPELINE
approved reference sheet
→ разметка конструкции
→ extraction отдельных деталей
→ очистка alpha
→ production assets
→ 2.5D assembly rig
→ animation states
→ FX
→ APK PlayerCheck
→ корректировка по фактическому виду в игре.

12. ЗАПРЕТЫ
Запрещено:
- вставлять целую reference sheet/Sphere как финальный sprite;
- возвращать старый procedural silhouette вместо утверждённого дизайна;
- самостоятельно придумывать новый силуэт при наличии approved reference;
- делать все детали статичными;
- накладывать независимую "декорацию", которая меняет идентичность Sphere;
- считать CI доказательством визуального качества. Визуал подтверждается APK PlayerCheck.

13. ПОРЯДОК РАБОТЫ
Сначала доводится одна Sphere до production-quality.
После ручного подтверждения в APK тот же pipeline переносится на следующие Sphere.
При споре между старой реализацией и approved reference sheet приоритет имеет утверждённый reference и фактическое наблюдение в APK, если это не противоречит игровой механике.
